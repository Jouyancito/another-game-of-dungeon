## El bug de color — diagnóstico con la causa exacta

`_glb_truth_render.py` ya documentaba este bug el 2026-07-29 y **sigue sin arreglarse**.

La diferencia entre el mob que funciona y los que no es de una línea:

```python
# rat/build_rat.py:247  -- FUNCIONA
me.color_attributes.new(name="Col", type="BYTE_COLOR", domain="POINT")
attr.attribute_name = "Col"
nt.links.new(attr.outputs["Color"], n.inputs["Base Color"])
```

El color es un **dato del vértice**, y el dato viaja dentro del glTF.

```python
# snake/build_snake.py:391  -- SE PIERDE
noise = nt.nodes.new("ShaderNodeTexNoise")
vor   = nt.nodes.new("ShaderNodeTexVoronoi")
geo   = nt.nodes.new("ShaderNodeNewGeometry")
```

El color es una **función evaluada por el motor de render de Blender**. glTF no puede expresar
un grafo procedural, así que `export_scene.gltf` lo descarta y escribe un
`baseColorFactor 1,1,1` — y **no falla al hacerlo**. El render de showcase del propio build
script muestra escamas, rayas y quitina; el juego recibe un mob blanco.

Es el mismo patrón que el resto de los errores de este proyecto: **una medición que no puede ver
lo que se le pregunta**. El showcase renderiza con el grafo puesto, así que nunca podía detectar
que el grafo no se exporta.

### Nota sobre `rat`: funciona, pero con un bug latente

Usa `BYTE_COLOR`. La skill `blender-asset-smith` documenta que el atributo BYTE aplica un
decode sRGB en la lectura que la escritura de bmesh no codifica, lo que **oscurece todo tono
elegido a mano ~12×**. La luma media medida de `rat.glb` es **0,287**. Hay que comparar contra
los valores que el script pretendía escribir antes de dar el color por bueno.
El fix conocido es `FLOAT_COLOR`, nunca `BYTE_COLOR`.

## Las dos vías para arreglar los cuatro rotos

Esto es una decisión de pipeline, y la dejo abierta para Joan en vez de elegirla solo — que es
exactamente el error que cometí hoy con el pelo.

| | **A. Bakear a vertex color** | **B. Bakear a textura** |
|---|---|---|
| Cómo | Cycles con `bake.target='VERTEX_COLORS'`, a un atributo FLOAT_COLOR | UV unwrap + bake de albedo a PNG |
| Sirve para | gradientes suaves, tono por zona | **patrones finos**: escamas, rayas, quitina |
| Cuesta | poco; ya es el patrón de los packs de vegetación | UVs headless + atlas + más peso |
| Límite duro | **la resolución es la malla**: serpiente tiene 152 vértices, no le cabe un patrón de escamas | ninguno relevante |
| Canon | patrón vigente de `flower_pack` / `grass_pack` | `_asset_creation_contract.md` §3b lo habilita: techo Skyrim = albedo + normal + roughness |

**Recomendación**: mixta. Vertex color para tortuga, avispa y ave (masas de tono); textura para
la serpiente, porque su patrón de escamas es justamente lo que la hace serpiente y **no cabe en
152 vértices**.

## Resultado del fix — ejecutado y verificado la misma noche

atributo **FLOAT_COLOR** con Cycles (`bake.target='VERTEX_COLORS'`, sólo pase de color, sin
directa ni indirecta: la luz es trabajo de Godot) y recablea Base Color para que lea el
atributo. Se corre sobre los `*_wip.blend` que los build scripts ya dejaban, así que **los
generadores quedaron sin tocar** hasta que el enfoque estuviera probado.
